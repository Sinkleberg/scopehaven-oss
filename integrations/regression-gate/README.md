# One-shot regression gate

Run an explicitly selected registered target once, save the run through the core store, and emit one JSON release decision. There are no packages to install and no scheduler. The gate uses `createRegistry`, `loadProfiles`, `createStore`, and `compareRuns` without changing their interfaces.

From the ScopeHaven project root, use the integrated launcher, which selects the reviewed project Node runtime:

```sh
./scopehaven gate \
  --target demo-repaired --out /absolute/private/dedicated/gate-directory
```

`--target` and an absolute `--out` are mandatory. `--require-model-identity` is optional and needs `--baseline` (see Model attribution below). `--report-only` is optional and needs a window (see Report-only below the exit table). `--trials N` is optional, with `--pass-k` and `--pass-k-floor` beside it (see Repeated trials below the exit table). `--self-test` (a switch, no value) runs the known-negative self-test over an HTTP contract target's profile before anything is sent: a check that cannot fail or always fails adds `check-cannot-fail` or `check-always-fails` (exit 1), and the summary carries the report as `selfTest` ([docs/SELF-TEST.md](../../docs/SELF-TEST.md)). The output parent must exist. A new output directory is created with mode `0700`; an existing directory must be empty and private, or already belong to this gate. A marker prevents accidental adoption of ordinary evidence directories. The project's `data/` directory is rejected. An exclusive lock prevents overlapping gate writers; core storage still assumes no unrelated writer process. A crash may leave `.gate-lock`: first confirm no gate is running before manually removing that lock. The gate never removes another invocation's lock.

For a configured local target, add `--config /absolute/path/to/targets.json`. Only a profile accepted by the core validator is usable; the gate accepts no URL argument, inline request body or arbitrary endpoint. Configuration is never inferred from `SCOPEHAVEN_TARGETS_FILE`. The CLI supplies environment references to the core credential resolver for the selected profile. The importable `runGate` defaults to an empty environment; pass `{ env }` explicitly if authorized credentials are required. No credentials are used by the example or tests. A loopback profile can still invoke the target application's own downstream dependencies: verify ownership, effects and isolation before running it.

Add `--baseline <run-id>` to compare against a run in the **same gate output directory**. Read/integrity/shape errors stop before another target run. Compatibility is established by the core comparison after the candidate runs; an incompatible baseline returns nonzero. Build labels may change but the contract/context identities must remain compatible. A baseline is optional, so a clean run without one makes no repair claim. Baselines are never updated automatically.

| Exit | Outcome | Meaning |
| --- | --- | --- |
| `0` | `clean` | Every current check passed; required allowed-use controls passed; any requested comparison is compatible and fully evaluated. |
| `1` | `assessment-failed` | Failed checks, missing/nonpassing controls, inconclusive or N/A evidence, incompatible baseline, an unverified comparison, a repair not credited to the application (`repair-not-attributable`), a model identity a run carries that cannot be read (`model-identity-malformed`), or, with `--require-model-identity`, a model-served comparison without a recorded identity on both runs (`model-identity-not-recorded`) or without a comparable identity held in Scopehaven's custody on both runs (`model-identity-unverified`), or, with `--self-test`, a check that cannot fail (`check-cannot-fail`) or always fails (`check-always-fails`), or, with `--trials`, a check that reads FAIL-flaky over the trials (`checks-flaky`, beside the trials' own reasons). |
| `2` | `config-or-runtime-error` | Invalid arguments/configuration/evidence (including `--require-model-identity` without `--baseline`, `invalid-options`; `--self-test` on a target other than an HTTP contract profile, `self-test-unsupported-target`, or a self-test that could not run, `self-test-error`; a `--trials` refusal, `trials-*` or `pass-k-*`), storage/integrity failure, missing credentials/baseline, or an error-status check in either compared run. |

**Report-only.** `--report-only` (a switch) with `--report-only-until YYYY-MM-DD`, `--report-only-runs N`, or both, is a rollout aid: while the window applies, an `assessment-failed` verdict exits `0` instead of `1`. Clean stays `0` and an error stays `2`.
- **The window.** It applies while today's UTC date is on or before the last day and this run is within the first N report-only runs recorded in the output directory, whichever ends first; after that the normal exit codes apply. One of the two bounds is required (`invalid-options` otherwise). Before anything is read or sent, N must be 1 to 100 and the date a real calendar date (`report-only-window-invalid` otherwise), and a date more than 90 days ahead is refused (`report-only-window-too-long`). A date already passed is accepted: that window has ended. Not with `--saved-refund`, which records no new run. `report-only.mjs`, and the report and SARIF renderers it loads, is imported only with the switch, so the gate's import closure is unchanged without it.
- **The count.** Runs are counted from `gate-summaries/` in the output directory, under the gate's lock: each saved summary whose window was not ended counts as used, and so does a summary that cannot be read or parsed, so accidental damage shortens a window. The count is only as good as that directory: deleting a summary, or editing one to drop its window, gives a run back. It guards against accidents, not against someone who can write the directory (who could as easily drop the switch). A window already used up stays used up there; start a new window in a new output directory.
- **The summary.** It carries `reportOnly` right after `schemaVersion`: `{ mode: 'report-only', state: 'applied' | 'ended', endedBy?: 'date-passed' | 'runs-used', until, runs, run?, exitCode, note }`. `outcome`, `exitCode` and `reasons` are the verdict's, exactly as without the switch, so the summary never reads as a pass; `reportOnly.exitCode` is the process exit. `runGate` returns the same object: a caller that sets its own exit from the summary should read `reportOnly.exitCode` when it is present.
- **Every page.** While the window applies, the gate also writes `gate-summaries/<run-id>.report-only.html` and `<run-id>.report-only.sarif`: the stored run rendered as `scopehaven export` renders it, then marked. The HTML has a REPORT-ONLY title, a banner on the cover, a line in each check and in the limits, and a header on each printed page where the browser supports page margin boxes. Each SARIF result message starts with `[REPORT-ONLY run: not a pass]` and the run's properties and invocation carry the window; levels, kinds and fingerprints are as recorded. These files are written before the summary, so a run whose marked files could not be written exits `2` (`report-only-output-error` or `report-only-stamp-failed`) and is not counted. The stored run is not changed: the mode is a gate decision, not run evidence, so a later `scopehaven export` of that run carries no mark. Use the gate's marked files while the window applies.
- The GitHub Action's `report-only` and `report-only-until` inputs use the same window (dates only) and also mark its exported reports; see the [Action guide](../github-action/README.md#report-only).

**Repeated trials and pass^k.** `--trials N` (2 to 100) runs an HTTP contract target N times, one after another under the same lock and authorization window, and reads a pass^k column per check over those N runs with the pass-k module ([pass-k README](../pass-k/README.md): pass^k = C(passed, k) / C(trials, k), tau-bench; an error, inconclusive or not-applicable trial is never a pass). `--pass-k K` (1 to N, default 1) is the k, and `--pass-k-floor F` (`1` or a reduced fraction below 1 such as `9/10`, default `1`) is the floor; both need `--trials`.

```sh
./scopehaven gate --target my-app --config /abs/targets.json --authorization /abs/authorization.json \
  --out /absolute/private/dedicated/gate-directory --trials 5 --pass-k 1 --pass-k-floor 1
```

- **Readings.** Each check reads `PASS` only when every trial passed and, on an operator-forwarded or remote target, every trial's pass was paired with a passing same-route required control (`src/forwarded-pairing.mjs`). A check that passed some trials and whose pass^k is below the floor reads `FAIL-flaky`, never `PASS`, and the gate adds `checks-flaky`. Otherwise a non-passing check reads `FAIL` (a trial failed it) or `NOT-PASSED` (no trial failed it, but not every trial passed cleanly, including a pass left unpaired in any trial: `unpaired: true`). A floor below 1 never makes a check `PASS` and never relaxes the verdict: every trial is judged as a single run would be and its reasons count (a leak on one trial in five gives `checks-failed` whatever the floor), so a floor below 1 only decides which mixed checks are named flaky.
- **Every trial is evidence.** Every trial is validated, and the pass^k column read over all of them, before any is stamped or saved; once the authorization window ends nothing more is sent and nothing is saved (`authorization-window-ended`). All N runs are saved in the store, each with the authorization stamp. The trials must share one trial identity (the pass-k module's: `compareRuns` stable keys, target, build, configuration, context, required controls and, when a run records a model identity, the one model it binds), or the gate refuses with `pass-k-trial-identity-differs` (or `pass-k-checks-differ`, `pass-k-invalid-trial-data`) and keeps nothing. A run whose model identity is partial, mixed or not observed binds no single model, so on such a target `--trials` is refused this way after the requests are sent.
- **The summary.** One summary per gate invocation, named by the first trial. `current`, the comparison (with `--baseline`), the self-test and the report-only window are the first trial's; `reasons` adds each other trial's reasons not already listed, in trial order, then `checks-flaky`. An error in any trial exits `2`. With `--baseline`, the comparison's counts are the first trial's, and its `restorationLabel` is withheld (`No verified repair`, with `restorationWithheld: 'not-every-check-passed-every-trial'`) unless every check reads `PASS`, so a repair one lucky trial shows is never credited. The summary's `trials` block is `{ schema: 'scopehaven-gate-trials/1', trials, k, floor, runIds, readings: { PASS, FAIL-flaky, FAIL, NOT-PASSED }, checks: [ { id, role, trials, passed, failed, undecided, k, floor, exact, passHatK, unpaired, floorMet, reading } ], perTrial: [ { runId, exitCode, reasons } ], passK, scope }`, where `passK` is the pass-k column without its per-check rows.
- **Report and SARIF.** The gate writes `gate-summaries/<first-run-id>.trials.html` and `.trials.sarif` before the summary (a run whose trial files could not be written exits `2`, `trials-output-error` or `trials-report-failed`/`trials-sarif-failed`). The HTML is the first trial's report, as `scopehaven export` renders it, with a pass^k section before the limits and each check's reading, pass^k and floor in its article. The SARIF is the first trial's, with the pass-k module's `properties.passK` on each result and the run, and `properties.passKGate` (`k`, `floor`, `reading`, `floorMet`, `unpaired`) on each result and on the run. A result whose reading is not `PASS` is never kind `pass`: kind `fail`, at its rule's level, when any trial failed it; otherwise a recorded pass becomes kind `review` when a trial's pass was unpaired (as `src/sarif.mjs` projects one) or kind `open`. Its message starts with the reading, then `First trial:` and the first trial's own message; `properties.scopehavenStatus` stays the first trial's recorded status. With report-only applied, both files are marked REPORT-ONLY too. A later `scopehaven export` of a stored run carries no trials: the column belongs to the gate invocation, not to one run.
- **Refusals, before anything is sent.** A value that is not a whole number of one to three digits (`--trials 0`, `--trials abc`, `--pass-k 0`) or a floor that is not digits and `/` (`0.9`) is `invalid-options`, as is `--pass-k` or `--pass-k-floor` without `--trials`. Then, before the configuration is read: `--trials` of 1 or above 100 (`trials-invalid`), k above N (`trials-k-invalid`), and a floor that is not `1` or a reduced fraction below 1 (`trials-floor-invalid`). After the configuration is read and before anything is sent: any target that is not an HTTP contract profile (`trials-unsupported-target`): the owned demo targets are scripted and give the same run each time, a conversation target carries its own trials inside one run, and a refund result is read, not run. Not with `--saved-refund`. `trials.mjs` is imported only with `--trials`, so the gate's import closure is unchanged without it.
- **Limits.** Trials are fresh runs made one after another; they are only as independent as the application and its state between runs, and correlated trials overstate pass^k. k and the floor are gate options, not profile keys: the profile schema feeds the HTTP evaluator identity, so moving them into the profile is a change for the next evaluator re-pin. The GitHub Action passes them through its `trials`, `pass-k` and `pass-k-floor` inputs (with `baseline-run`), copies `trials.html` and `trials.sarif` into its evidence artifact and renders the `trials` block in its job summary ([../github-action/README.md](../github-action/README.md), "Repeated trials").

Counts are recomputed from unique result rows and checked against the declared totals. Passing assertions and evidence structure, required controls, expected registered suite coverage, identity/hash fields and comparison shape are validated. Passing synthetic effects are rechecked with the core `evaluateCheck` and `CHECKS` definitions. HTTP observation digests, request/transport state, duplicate observation fields, HTTP status assertions and JSON predicate outcomes must agree; the registered suite also supplies assertion kinds, method and evidence requirements. A complete non-JSON response can satisfy a status-only contract, while unavailable JSON cannot satisfy a JSON predicate. This rejects contradictory or incomplete evidence even with recomputed digests or a declared failure count of zero. Minimized metadata cannot re-evaluate private predicate values or attest a target's truthfulness; validation does not prove arbitrary retained evidence true or override the core evaluators.

**Sequence runs.** The gate also judges saved timed-sequence runs (evidence origin `local-sequence`), through the sequence CLI: `./scopehaven sequence ... --save DATA_DIR --build LABEL --regression-gate [--baseline RUN_ID]` (see [Judge a run with the regression gate](../sequences/README.md#judge-a-run-with-the-regression-gate)). `--target` runs remain registry-only.
- **Validation.** `validateRun` hands a `local-sequence` run to `integrations/sequences/native.mjs`, which rebuilds the native run from the sealed `scopehaven-sequence-run/3` record it carries after recomputing every verdict. Any disagreement is refused as `invalid-sequence-evidence`, with the part as detail. A run of another origin that carries `sequenceEvidence` is invalid evidence.
- **Binding.** With the expected suite the sequence CLI exports, the candidate must match the scenario hash, assertions, status assertions, target (sequence id, `applicationId`, `contextId`), the current sequence evaluator hash and the declared observers. Otherwise: `unexpected-suite-evidence`.
- **Comparison.** A pair with a sequence run on either side is compared by `compareSequenceRuns` instead of the core `compareRuns`, in the core's shape. It is incompatible unless the evaluator hash, scenario hash, sealed assertion definitions, target and observers all match; the build label may differ.
- **Labels.** A restored effect row reads `local-control-restored`, and a restored response-status row `contract-restored`. The pair's repair label is `Observed effects restored`, `Response status restored`, or both. A row inconclusive on either side reads `unverified` (the gate reports `comparison-incomplete`), and a pair whose controls did not all pass reads `Unverified changes`.
- **Scope.** Effect rows are decided from the declared observers, where a boundary pass needs a deciding observer held outside the application (custody). Status rows are the status codes the application answered, never reply text. Sequence runs carry no separate login proof, so the gate's own `identity-not-established` reason never applies to them. Instead, a refusal row is response-level evidence, and it passes only when an earlier request by the same actor in the same run was accepted (2xx); otherwise it reads inconclusive (`identity-not-established`), so the gate is not clean and the comparison gives it no restoration credit.
- **Loading.** The gate loads the sequence module when `integrations/sequences` is present. A copy of the gate without it refuses sequence runs (`sequence-evidence-unavailable`) and judges every other origin as before.
- **Core comparison.** The core comparison and the dashboard do not know this origin: they read a sequence pair as unsupported, never as a repair. The core store's history summary does not strip `sequenceEvidence` yet, so a history listing of such a run includes the sealed run.

**Model attribution.** For HTTP response runs (`local-http-response`), the core comparison reports whose change a verdict change is, when both runs carry a model identity (`modelIdentity`, from `integrations/model-identity`):
- The gate fails with `repair-not-attributable` when a repair is not credited to the application: the model changed, both may have changed, or the model was not observed comparably.
- HTTP runs carry the declared build label, not a build hash. So a model swap under an unchanged label reads `confounded`, and a repair under an unchanged label with the same model reads `unexplained` (run-to-run variation). Neither is credited.
- Without identity on both runs, the comparison says `not-recorded` and the gate decides as before; a verdict change may then come from the model. Conversation runs are not attributed yet, because their build is part of the compatibility keys.
- Only HTTP response comparisons carry `modelAttribution`. Fixture and conversation comparisons have no such field.
- A supplied comparison must carry the same attribution the gate recomputes. One saved before attribution existed is accepted only where the recomputed one reads `not-recorded`.
- A model identity that a run carries but that cannot be read (a malformed entry, or attribution that failed on it) fails the gate with `model-identity-malformed`, and the summary names the side (`modelAttribution.malformed`). It never reads as "no identity".
- A comparison saved by an earlier release is refused as invalid evidence (exit 2) when the attribution the gate recomputes has changed shape since. That covers an incompatible pair with a recorded identity (its `flipCause` is now `null`) and a pair with an unreadable identity (its repair label is now withheld). This fails closed. Regenerate saved comparisons with the current release rather than editing them.
- `--require-model-identity` (a switch, no value) makes identity mandatory for model-served comparisons, and needs `--baseline`: without one the gate refuses it as `invalid-options` (exit 2), as the GitHub Action refuses it. A run with no baseline makes no repair claim, so the switch would decide nothing. With the switch:
  - without a recorded identity on both runs the gate fails with `model-identity-not-recorded` (and, for an identity a run carries but that cannot be read, `model-identity-malformed` beside it);
  - an identity that is partial, mixed, requested-only or not observed, or whose custody is not `tap-memory`, fails with `model-identity-unverified`. A different or silently changed model is comparable: the attribution rules above decide, and a repair under a model change fails with `repair-not-attributable`;
  - the summary's `comparison.modelIdentityPolicy` says whether the policy was met and, if not, why, as `{ side, reason }` codes (for example `{ "side": "candidate", "reason": "subject-writable-custody" }`).
  - When the policy is not met, the gate summary credits no repair: `modelAttribution.repairCreditedToApp` reads `false` with `policy: 'not-met'`, and a repair label that could stand reads `Not attributable to the application: the model identity policy was not met`.
  - What the switch cannot see: it reads a stored run's identity and custody as the run's file records them. The run digest is a checksum, not a signature: a baseline edited to the candidate's model and resealed, or a `tap-file` baseline relabelled `tap-memory` and resealed, passes the policy. Keep `baseline-run` where the application and its authors cannot write it; signing or anchoring the identity when it is captured is future work. The tap also sees only calls sent to its port: an application that sends one call through the tap and its real calls straight to the model server meets the policy. The policy holds only where routing enforced outside the application leaves the tap port its only way to the model server.
  Without the switch, deleting `modelIdentity` from both runs makes a comparison read `not-recorded`, and the gate decides as before. A `tap-file` identity never credits a repair, with or without the switch: where it shows the model held constant, the verdict changes read `model-unverified`. Comparisons that are not attributed are unaffected: runs whose subject no model serves, and conversation runs, which are not attributed yet (see above).
- **Where the identity comes from.** The HTTP connector writes `modelIdentity` when a model tap is configured. With `SCOPEHAVEN_MODEL_TAP_UPSTREAM` (a literal loopback origin) and `SCOPEHAVEN_MODEL_TAP_PORT` in the gate's environment, the gate starts the tap in its own process for the assessment, marks it at both ends and stops it; the application's model base URL points at `http://127.0.0.1:PORT` and needs no tap control. That identity carries custody `tap-memory`. `SCOPEHAVEN_MODEL_TAP_LOG` instead reads a closed tap log file another process wrote: custody `tap-file`, which any process running as the log's user can rewrite and re-chain, so the switch reads it unverified (`subject-writable-custody`). An operator-run tap is still open when the run ends, so that route reads partial (`tap-log-not-closed-at-end`) anyway. Without any of these settings, runs carry no `modelIdentity`. See [model identity](../model-identity/README.md) and the [GitHub Action](../github-action/README.md#model-identity).

The JSON summary is deterministic for the same evidence. Run UUIDs naturally change on each execution. It contains current counts, scope, allowed-control status, baseline compatibility, the core comparison counters and an explicit count of each core transition label. `comparison.restorationLabel` is the evidence scope's repair label only when the pair is compatible, the candidate's required allowed-use controls all passed, at least one row was restored, no check that passed in the baseline failed in the candidate, and no row is unverified or not applicable (the condition the gate reports as `comparison-incomplete`). A compatible pair whose controls passed but that restored nothing, introduced a new failure or left a row unverified or not applicable reads `No verified repair`. An incompatible or controls-failed pair reads `Unverified changes`. If either run carries an identity that cannot be read, a compatible pair whose controls passed reads `Not attributable to the application: a model identity was present but could not be read`. With readable identities on both runs, attribution can replace the label of a compatible pair, `Unverified changes` included, with `Not attributable to the application: <why>`, or append a vendor-identity caveat. `current.restorationLabel` always names the candidate's evidence scope. `fixed` refers only to owned synthetic backend evidence. `contract-restored` refers to HTTP response predicates and never claims verified backend effects. The core's combined `summary.fixed` counter is preserved, with the separate labels and scope preventing those meanings from being conflated.

The summary excludes names, titles, request/response bodies, traces, editable notes, paths, raw exceptions and credential references. Run IDs and the configured target ID are retained; choose a nonsensitive target ID. Safe fixed reason codes replace exception text. Full run evidence remains in the private core store; the gate does not broaden the core's evidence retention policy.

Completed decisions are written once to `gate-summaries/<run-id>.json` with mode `0600` (with report-only applied, beside the run's marked `.report-only.html` and `.report-only.sarif`), beside the core's immutable `runs/` and separate `notes/`. A storage failure can occur after the target has run or core evidence has been saved; exit `2` is not proof that no action occurred. Inspect the private store and target before a manual rerun. The gate performs no retry, reset, automatic baseline promotion or recurring work. The owned fixture itself includes its existing explicit idempotency/reconciliation scenarios.

```sh
./scopehaven gate-demo
.runtime/node-v24.21.0-darwin-arm64/bin/node integrations/regression-gate/launcher-acceptance.mjs
```

The demonstration expects the vulnerable fixture's assessment to fail, then requires a clean repaired comparison. It emits a compact receipt and removes its temporary evidence directory. `demo-result.json` records the actual demonstration performed for this implementation; its raw run files were temporary. The launcher acceptance checks the integrated command's actual exits against owned synthetic/HTTP fixtures, verifies private saved summaries and source hashes, and removes its temporary evidence. `launcher-acceptance-result.json` records that execution. `ci-invocation.sh.example` is inert text illustrating a future local/CI invocation; it installs nothing and enables no workflow. See [RECURRING-CHECKS.md](RECURRING-CHECKS.md) for the decisions and operational verification still needed before recurring checks.

Import `runGate`, `summarizeGate`, `validateRun`, `validateComparison`, `parseArgs`, or `EXIT` from `gate.mjs`. `runGate(options, { env, now })` returns the same JSON object as the CLI, with `exitCode` (`now`, a `Date`, defaults to the current time and dates the report-only window). The pure summary/validation functions accept core evidence; callers loading evidence themselves must use the core store for integrity verification. Core owns package/launcher/server/dashboard wiring; the supported launcher commands are `gate` and `gate-demo`. Direct Node execution of `cli.mjs` and `demo.mjs` remains supported with the reviewed runtime. An API summary of saved evidence is not a new gate assessment or a scheduled run; verification of that authenticated boundary belongs to the core integration tests.
